# Техническое задание на разработку Java REST микросервиса для системы учета оборудования и материалов

## 1. Введение

### 1.1. Цель документа
Настоящее техническое задание (ТЗ) определяет требования к разработке Java REST микросервиса для системы учета оборудования и материалов в организации среднего размера (до 500 сотрудников). Микросервис предназначен для автоматизации процессов регистрации, учета, перемещения и отчетности по объектам оборудования и материалам, а также управления пользователями (сотрудниками). Документ обновлен с учетом дополнительных рекомендаций: импорт/экспорт данных, продвинутые фильтры и поиск, валидация и бизнес-логика, расширенная история и аудит, роли и аутентификация с интеграцией, каскадные операции и проверки, динамические справочники с иерархией и локализацией, а также мониторинг и безопасность.

### 1.2. Обзор системы
Система представляет собой RESTful микросервис, реализованный на языке Java с использованием фреймворка Spring Boot. Микросервис должен обеспечивать:
- Регистрацию и управление объектами оборудования/материалов.
- Учет пользователей (сотрудников).
- Генерацию отчетов.
- Редактирование справочников (категории объектов, статусы, типы контрактов).
- Хранение истории действий для обеспечения аудита.
- Импорт/экспорт данных в различных форматах.
- Продвинутый поиск и фильтрацию.
- Валидацию данных и бизнес-логику.
- Интеграцию с внешними системами (аутентификация, брокеры сообщений).
- Мониторинг и безопасность.

Микросервис должен работать с реляционной базой данных (рекомендуется PostgreSQL). Для поиска и аудита рекомендуется интеграция с Elasticsearch/Kibana как отдельным микросервисом. Для асинхронной коммуникации и стабильности — брокер сообщений Kafka. API должно быть защищено (Spring Security с JWT/OAuth, интеграция с SSO Google из материнского проекта).

### 1.3. Требования к технологиям
- Язык программирования: Java 21.
- Фреймворк: Spring Boot 3.x, Spring Data JPA для работы с БД, Spring Web для REST API.
- База данных: PostgreSQL (или аналогичная реляционная СУБД).
- Поиск и аудит: Elasticsearch/Kibana (отдельный микросервис).
- Брокер сообщений: Apache Kafka для асинхронной коммуникации между сервисами и логирования событий.
- Импорт/экспорт: Apache POI для CSV/Excel, Jackson для JSON, iText для PDF. Для интеграции с другими сервисами — технологии вроде WSDL и Apache CXF (для SOAP-совместимости, если потребуется).
- Аутентификация: Spring Security с JWT/OAuth, интеграция с SSO Google.
- Мониторинг: Spring Boot Actuator для метрик, интеграция с Prometheus/Grafana.
- Формат обмена данными: JSON.
- Документация API: Swagger/OpenAPI.
- Тестирование: Unit-тесты (JUnit), интеграционные тесты.
- Деплой: Docker-контейнеризация.

## 2. Функциональные требования

Система разделена на модули. Каждый модуль реализуется через REST API эндпоинты. Все операции должны логироваться для аудита через Kafka и Elasticsearch.

### 2.1. Модуль регистрации объектов
Модуль обеспечивает создание, редактирование, просмотр и перемещение объектов оборудования/материалов. Объекты могут быть в статусе: "исправно", "на хранении", "поломано", "списано". Категории объектов — фиксированные (около 10 шт., редактируемые в отдельном модуле, например: "компьютеры", "мебель", "инструменты" и т.д.).

**Обязательные параметры объекта:**
- Производитель (строка).
- Дата выпуска (дата).
- Дата ввода в эксплуатацию (дата).
- Статус (enum: WORKING, STORED, BROKEN, WRITTEN_OFF).
- Информация о текущем владельце/пользователе (ссылка на пользователя или "склад").
- Инвентарный номер (уникальная строка).
- Серийный номер (уникальная строка, опционально).
- Категория (ссылка на категорию).

**Функционал:**
- Создание объекта (POST /api/objects).
- Редактирование объекта (PUT /api/objects/{id}).
- Просмотр объекта (GET /api/objects/{id}).
- Просмотр списка объектов (GET /api/objects с фильтрами: по категории, статусу, владельцу).
- Механизм перемещения: POST /api/objects/{id}/transfer с параметрами (toUserId или toWarehouse). При перемещении создается запись в истории.
- Хранение истории: Каждая операция (создание, редактирование, перемещение, изменение статуса) сохраняется в отдельной таблице. Отчет по истории: GET /api/objects/{id}/history (возвращает список действий с датами, от кого/кому, детали).
- Каскадные операции и проверки: При изменении статуса пользователя (например, на "неактивный") — автоматический перевод связанных объектов на склад. Каскадные проверки уникальности и целостности данных при операциях с объектами и пользователями.

**Дополнительно:**
- Валидация и бизнес-логика: Уникальность инвентарного/серийного номера, проверка дат. Шаблоны для данных (например, формат телефона через regex). Реализация на бэкенде (Hibernate Validator) и фронтенде (для UX).
- Продвинутые фильтры и поиск: Многофакторный поиск по нескольким полям (имя, категория, статус) с пагинацией (page, size), сортировкой и полнотекстовым поиском через Elasticsearch (GET /api/objects/search?query={query}&page=0&size=20&sort=inventoryNumber,asc).

Отношения: Один объект принадлежит одному пользователю (или складу). Пользователь может владеть несколькими объектами (OneToMany с каскадными операциями).

### 2.2. Модуль учета пользователей
Модуль управляет данными о сотрудниках. Удаление пользователя не физическое — статус меняется на "неактивный" для сохранения истории.

**Параметры пользователя:**
- Имя (строка).
- Фамилия (строка).
- Должность (строка).
- Телефон (строка).
- Идентификационный номер (уникальная строка).
- Дата поступления на работу (дата).
- Дата окончания контракта (дата, опционально).
- Тип контракта (ссылка на тип контракта).
- Текущий статус (enum: ACTIVE, INACTIVE).

**Функционал:**
- Добавление пользователя (POST /api/users).
- Редактирование пользователя (PUT /api/users/{id}).
- "Удаление" (изменение статуса на INACTIVE): DELETE /api/users/{id} (или PATCH для статуса).
- Просмотр пользователя (GET /api/users/{id}).
- Просмотр списка пользователей (GET /api/users с фильтрами: по статусу, должности).
- Просмотр объектов пользователя: GET /api/users/{id}/objects.

**Дополнительно:**
- Валидация и бизнес-логика: Уникальность идентификатора, шаблоны для имен, телефонов (regex). Реализация на бэкенде и фронтенде.
- Продвинутые фильтры и поиск: Многофакторный поиск через Elasticsearch (GET /api/users/search?query={query}).
- Каскадные операции: При "удалении" — перевод объектов на склад.
- История изменений: Таблица user_history для аудита, аналогично объектам.
- Роли и аутентификация: Интеграция с материнским проектом (Spring Security с JWT/OAuth, SSO Google). Связь "пользователей объектов" с аккаунтами (синхронизация ID или маппинг). Роли: admin (полный доступ), user (просмотр/редактирование своих объектов). Эндпоинты: /api/auth/login с RBAC.

Отношения: Пользователь может иметь несколько объектов (OneToMany).

### 2.3. Модуль отчетности
Модуль генерирует отчеты в формате JSON (с возможностью экспорта в CSV/PDF через дополнительные эндпоинты).

**Функционал:**
- Отчет по всем объектам: GET /api/reports/objects (с опциональными фильтрами: категория, статус).
- Отчет по объектам категории: GET /api/reports/objects?categoryId={id}.
- Отчет по пользователю и его объектам: GET /api/reports/users/{id}/objects.
- Отчеты должны включать суммарные данные (количество объектов, статусы и т.д.).

**Дополнительно:**
- Экспорт: Интеграция с импорт/экспорт сервисом для CSV, JSON, PDF.

### 2.4. Модуль редактирования категорий объектов
Модуль для CRUD операций над категориями (справочник).

**Функционал:**
- Создание категории (POST /api/categories).
- Редактирование (PUT /api/categories/{id}).
- Удаление (DELETE /api/categories/{id} — с проверкой, что категория не используется).
- Просмотр списка (GET /api/categories).

**Дополнительно:**
- Динамические справочники: Поддержка иерархии (подкатегории, parent_id в таблице). Локализация (многоязычные названия, поле для translations JSON).

### 2.5. Модуль редактирования статусов и типов контрактов пользователей
Модуль для CRUD операций над типами контрактов и статусами пользователей (справочники). Статусы объектов также редактируемы.

**Функционал (для типов контрактов):**
- Создание (POST /api/contract-types).
- Редактирование (PUT /api/contract-types/{id}).
- Удаление (DELETE /api/contract-types/{id} — с проверкой использования).
- Просмотр (GET /api/contract-types).

**Функционал (для статусов пользователей):**
- Создание (POST /api/user-statuses).
- Редактирование (PUT /api/user-statuses/{id}).
- Удаление (DELETE /api/user-statuses/{id}).
- Просмотр (GET /api/user-statuses).

**Функционал (для статусов объектов):**
- Аналогично, POST/PUT/DELETE/GET /api/object-statuses.

**Дополнительно:**
- Динамические справочники: Иерархия и локализация, как для категорий.

### 2.6. Модуль импорта/экспорта данных
Отдельный микросервис (для переиспользования в других частях системы) для импорта/экспорта данных.

**Функционал:**
- Импорт: POST /api/import с MultipartFile (CSV/JSON). Парсинг и валидация данных перед вставкой.
- Экспорт: GET /api/export?type={objects/users}&format={csv/json/pdf}.
- Технологии: Apache POI (CSV), Jackson (JSON), iText (PDF). Для интеграции — WSDL/Apache CXF (если нужны SOAP-интерфейсы для других сервисов).

## 3. Структура базы данных

База данных реляционная. Ниже описаны таблицы с полями, типами данных и связями. Используйте JPA-сущности для mapping. Для аудита — интеграция с Elasticsearch.

### 3.1. Таблицы

1. **objects** (Объекты оборудования/материалов)
   - id: BIGINT PRIMARY KEY AUTO_INCREMENT
   - manufacturer: VARCHAR(255) NOT NULL
   - release_date: DATE NOT NULL
   - commissioning_date: DATE NOT NULL
   - status_id: BIGINT NOT NULL (FK to object_statuses)
   - current_owner_id: BIGINT (FK to users; NULL для склада)
   - inventory_number: VARCHAR(50) UNIQUE NOT NULL
   - serial_number: VARCHAR(50) UNIQUE
   - category_id: BIGINT NOT NULL (FK to categories)
   - created_at: TIMESTAMP DEFAULT CURRENT_TIMESTAMP
   - updated_at: TIMESTAMP

2. **object_history** (История действий над объектами)
   - id: BIGINT PRIMARY KEY AUTO_INCREMENT
   - object_id: BIGINT NOT NULL (FK to objects)
   - action_type: VARCHAR(50) NOT NULL
   - timestamp: TIMESTAMP DEFAULT CURRENT_TIMESTAMP
   - from_owner_id: BIGINT
   - to_owner_id: BIGINT
   - details: TEXT
   - user_id: BIGINT (FK to users, кто выполнил)
   - ip_address: VARCHAR(45)
   - INDEX on object_id

3. **users** (Пользователи/сотрудники)
   - id: BIGINT PRIMARY KEY AUTO_INCREMENT
   - first_name: VARCHAR(100) NOT NULL
   - last_name: VARCHAR(100) NOT NULL
   - position: VARCHAR(100)
   - phone: VARCHAR(20)
   - identification_number: VARCHAR(50) UNIQUE NOT NULL
   - hire_date: DATE NOT NULL
   - contract_end_date: DATE
   - contract_type_id: BIGINT NOT NULL (FK to contract_types)
   - status_id: BIGINT NOT NULL (FK to user_statuses)
   - created_at: TIMESTAMP DEFAULT CURRENT_TIMESTAMP
   - updated_at: TIMESTAMP

4. **user_history** (История пользователей)
   - Аналогично object_history: id, user_id, action_type, timestamp, details, ip_address.

5. **categories** (Категории объектов)
   - id: BIGINT PRIMARY KEY AUTO_INCREMENT
   - name: VARCHAR(100) UNIQUE NOT NULL
   - parent_id: BIGINT (FK to categories, для иерархии)
   - translations: JSONB (для локализации)

6. **object_statuses** (Статусы объектов)
   - id: BIGINT PRIMARY KEY AUTO_INCREMENT
   - name: VARCHAR(50) UNIQUE NOT NULL
   - translations: JSONB

7. **user_statuses** (Статусы пользователей)
   - id: BIGINT PRIMARY KEY AUTO_INCREMENT
   - name: VARCHAR(50) UNIQUE NOT NULL
   - translations: JSONB

8. **contract_types** (Типы контрактов)
   - id: BIGINT PRIMARY KEY AUTO_INCREMENT
   - name: VARCHAR(100) UNIQUE NOT NULL
   - translations: JSONB

### 3.2. Взаимосвязи
- objects.category_id → categories.id (ManyToOne)
- objects.status_id → object_statuses.id (ManyToOne)
- objects.current_owner_id → users.id (ManyToOne)
- object_history.object_id → objects.id (ManyToOne)
- object_history.user_id → users.id
- user_history.user_id → users.id
- users.contract_type_id → contract_types.id (ManyToOne)
- users.status_id → user_statuses.id (ManyToOne)
- categories.parent_id → categories.id (для иерархии)

Для склада: Специальный пользователь с id=0 или name='Склад'.

## 4. Нефункциональные требования
- Производительность: Поддержка до 10 000 объектов и 500 пользователей. Индексы на фильтруемые поля, кэширование (Spring Cache).
- Безопасность: Аутентификация, авторизация (роли). Защита от уязвимостей (OWASP, rate limiting).
- Логирование: Все операции в историю через Kafka в Elasticsearch. Трассировка изменений с IP и аккаунтами.
- Ошибки: Стандартизированные HTTP-ответы.
- Мониторинг: Spring Boot Actuator для метрик.
- Интеграции: Kafka для коммуникации между микросервисами. Синхронизация с материнским проектом (SSO).
